Real-time transcription and field extraction app. Analysis date: 2026-11-20. Folder: Voice_data_extraction/Real_time_transcription

1. What it does

A local Flask and Socket.IO web app for monitoring a live call (for example on Teams). It works in three steps:

  1. Capture audio from two sources: the microphone ("Caller-1") and the system audio output ("Caller-2", the remote party).
  2. Transcribe both streams in real time with Azure Speech-to-Text. Partial and final results appear as chat bubbles.
  3. Extract fields. Every few seconds the whole transcript is sent to Azure OpenAI (gpt-4o, JSON mode). The reply fills a form: Bank Account Number, Routing Number, Payment Date, Payment Amount.

On Stop, the app uploads the transcript .txt to Azure Blob Storage, runs a final extraction, and appends one row to an Excel file in Blob Storage. The Save button does the same for manually edited values.

Local requirements: Windows (WASAPI loopback is Windows-only), a microphone, and:

No other API keys are needed. LangChain is unused.

4. Gaps and issues

Security

  • Keys hardcoded in three files.
  • cors_allowed_origins="*" and no authentication. Anyone who can reach the server can start recording and write to storage.
  • The UI inserts transcript text with innerHTML, so injected content could run script (XSS).

Deployment contradiction

  • Configured for Azure App Service, but a cloud server has no microphone or system audio. The capture code only works on the user's own Windows machine. A hosted version needs browser-based audio capture.

Correctness

  • The whole transcript is re-sent to the LLM every 3 seconds. Cost and latency grow with call length.
  • Each extraction overwrites the form, including with blanks. Earlier found values can vanish and manual edits get overwritten.
  • Global state (conversation_log, recording_active) is shared across all browser clients. A second user interferes with the first.
  • A new auto_extract_worker thread starts on every Start. Quick stop and start can leave duplicate workers.
  • clear_conv replaces the log without taking the lock.
  • Excel save is a race condition. It downloads the file, appends a row and re-uploads, so concurrent saves lose data. It also swallows every read exception, so a transient error overwrites the file with a single row.
  • Stop always saves a row, even when extraction is empty or failed, and even if you already saved manually.
  • No validation or normalisation: routing numbers (9 digits, ABA checksum), account numbers, dates and amounts are free text. Spoken digits depend entirely on the LLM.
  • The prompt has no guidance on speaker roles, corrections ("no, I meant...") or confidence.
  • Transcripts are stored unredacted. Bank details are sensitive: no PII masking, retention policy or consent notice.
  • No real diarization: speakers are just "mic" and "system audio". Several remote participants are not separated.
  • The echo filter is heuristic (SequenceMatcher at 0.72) and can drop legitimately repeated phrases such as "yes".
  • Speech language is the default en-US. Indian-English or multi-language calls need an explicit language or auto-detect.
  • No logging framework, tests, health checks or UI reconnect handling. gunicorn needs an eventlet or gevent worker for Socket.IO.

Project hygiene

  • Three copies of the app, a commented-out 487-line block, dead lchain.py, a mismatched requirements.txt, __pycache__ checked in, and the folder is not a git repository.

5. Adapting it to a different set of fields

The field set is hardcoded in four places:

LocationWhat to change

save_to_excel() (line 591)Column names and function signature.
ui.pyForm inputs (lines 128-146), update_form_fields, clear_form_fields, show_popup, refreshConversation, saveFormData.
Socket.IO payloadssave_form_data, stop_recording, auto_extract_worker.

Recommended refactor (about half a day)

Define the schema once and generate everything from it:

# fields.py
FIELDS = [
  {"key": "customer_name",  "label": "Customer Name",   "type": "string", "hint": "Full name as stated by the caller"},
  {"key": "dob",            "label": "Date of Birth",   "type": "date",   "hint": "DD/MM/YYYY"},
  {"key": "policy_number",  "label": "Policy Number",   "type": "string", "hint": "digits only"},
]
  • Build the LLM prompt and a JSON schema from FIELDS. Use Azure OpenAI structured outputs (response_format with json_schema, strict: true) instead of plain JSON mode.
  • Return a dict, not a tuple. Write Excel columns from FIELDS.
  • Send FIELDS to the browser on connect and render the form dynamically.
  • Keep one prompt block per use case so you can switch (USE_CASE=insurance_claim) without code changes.

6. Enhancements, in priority order

  1. Security first: rotate keys; use .env or Azure Key Vault with managed identity (DefaultAzureCredential); add authentication (Entra ID or login); restrict CORS; escape transcript text in the UI (textContent).
  2. Config-driven fields (section 5), plus per-field validators (regex, ABA checksum, date parsing) and a confidence score or evidence quote per field.
  3. Better extraction: send only new turns plus current known values and merge (overwrite only when the new value is non-empty and changed); lock fields the user edited; extract only when new final utterances arrive; use a cheaper model (gpt-4o-mini) for live updates and gpt-4o for the final pass.
  4. Per-session state: replace globals with a Session object keyed by the Socket.IO session ID. Add a session ID to every saved row.
  5. Reliable storage: use Azure Table Storage, Cosmos DB or SQL instead of Excel read-modify-write; export to Excel on demand. If keeping Excel, use a blob lease or append-only CSV.
  6. Real diarization: Azure Speech ConversationTranscriber, or stereo channels from a call recording. Add language auto-detect, phrase lists for domain terms (PhraseListGrammar) and profanity or PII masking.
  7. Make it deployable: capture audio in the browser (getUserMedia for mic, getDisplayMedia for tab audio) and stream to the server over Socket.IO, removing the Windows and PyAudio dependency. For telephony, consider Azure Communication Services call recording or media streaming.
  8. Call-level features: summary, sentiment, compliance checklist (for example "agent verified identity: yes/no", as lchain.py hinted), action items, audit log.
  9. Operational quality: consolidate to one app.py, delete dead files, pin requirements.txt, use logging, run with gunicorn -k eventlet, add tests for extraction and validators, put it in git.
  10. Compliance: call-recording consent prompt, PII redaction before storage, retention policy, encryption at rest (Storage enables this by default).

8. Solution design deep-dive (vendor-neutral)

Confirmed constraints: local Windows desktop only; other STT vendors acceptable; live (during-call) extraction required.

Principle: five thin, swappable seams

SeamInterfaceTodayWhy
1. Audio sourceyields PCM chunks per channelPyAudio mic + WASAPI loopbackKeep as is (local only)
2. Transcriberstream(audio) -> {speaker, text, final}Azure Speech SDKAccuracy, latency and diarization differ by vendor and audio
3. Extractorextract(schema, new_turns, current_values) -> dictgpt-4o JSON mode on full transcriptCost, correctness, flexible field sets
4. Storesave(session_id, record, transcript)Excel read-modify-write in BlobRace conditions, no queries
5. Schemafields.py list used by 2-4 and the UIHardcoded in four placesNew use case with no code change

Each seam is 10-40 lines. No frameworks or orchestration layers.

Market developments that matter

Sources are mostly vendor docs and blogs, so treat accuracy claims as directional and benchmark on your own audio.

  • Strict structured outputs are standard. response_format: json_schema with strict: true (needs additionalProperties: false) guarantees schema-valid output. Cheap upgrade, no new service. Azure docs
  • Diarization-aware models exist (gpt-4o-transcribe-diarize), but sources conflict on whether they work on the realtime streaming path. Azure Speech Conversation Transcription is the documented live-diarization route. Verify before depending on it. MS guide, OpenAI model page
  • Streaming STT is crowded and converging. Azure Speech, Deepgram, AssemblyAI and Speechmatics all offer streaming with diarization. Benchmark rankings disagree depending on who ran them (WER roughly 4-9%). Choose by testing on your own calls. Deepgram, AssemblyAI
  • Managed audio-to-fields services exist. Azure Content Understanding audio analyzers do transcription, diarization and custom field extraction, but are in preview and post-call oriented. Optional comparison for the final pass, not for live updates. MS overview
  • Small, fast LLMs are good enough for live extraction. Use a mini-class model live and a larger model for the final pass.

Recommended design

  • Extraction (highest value, lowest effort): trigger on each new final utterance (debounce about 2 s) instead of a timer. Send schema + current values + last N turns, and get back only changed fields using strict JSON schema generated from fields.py. Merge rule: overwrite a field only if the new value is non-empty and not user-edited; keep an evidence quote and confidence per field. Plain-Python validators per field type (ABA checksum, dates, amounts, regex) flag values that models mishear.
  • Transcription: Azure Speech stays the default behind the seam, plus one alternative adapter (Deepgram or AssemblyAI) chosen by env var. Run a bake-off on 5-10 real recorded calls before choosing. Use channel-based speaker roles (mic = agent, loopback = customer), phrase lists for domain terms and an explicit language.
  • Storage: append-only SQLite with transcript, record, per-field evidence, session ID and prompt/model version. Excel becomes an on-demand export.
  • Cross-cutting: .env secrets (after rotating the exposed keys), a per-session state object, UI XSS fix, PII and consent notice, logging, pytest for validators and the merge rule, and a replay script over 10-20 labelled transcripts to measure per-field accuracy when prompts or models change.

Deliberately not recommended

  • LangChain or agent frameworks: one function call per extraction does not need them.
  • Vector DB or RAG: nothing here needs retrieval.
  • Microservices or queues: one Flask process is enough on a local desktop.
  • Realtime speech-to-speech voice-agent APIs: this is a listen-only monitor.
  • Hard dependency on one STT vendor or on a preview service.

Implementation order

  1. Rotate keys, create .env, consolidate to a single app.py based on app_updated.py, delete dead files.
  2. fields.py with dynamic form, schema-driven prompt and storage.
  3. Incremental strict-schema extraction, merge rule, validators.
  4. Per-session state, SQLite and Excel export, XSS and auth basics.
  5. STT adapter and bake-off.

Verification

  • Play a recorded call through the speakers while talking into the mic: both speakers appear, fields fill incrementally without flicker, and edited fields are not overwritten.
  • Replay labelled transcripts and compare per-field accuracy before and after changes.
  • Unit tests for validators and the merge rule.
  • Drop the network mid-call: recognizers restart, and concurrent saves lose no data.
